# Issue作成 (litom/egp)

このリポジトリでGitHub Issueを作る一連の作業を、リポジトリの慣習に沿って行う。

## 手順

### 1. 内容の把握

ユーザーが何についてissueを立てたいのか確認する。会話の文脈（直前に話していたバグ・要望・タスクなど）から明確な場合はそれを使い、不明瞭な場合はユーザーに聞く。

### 2. ラベルの選定

`gh label list` で既存ラベルを確認し、内容に合うものを選ぶ:

```
bug / documentation / duplicate / enhancement / good first issue / help wanted / invalid / question / wontfix / refactor
```

どれもしっくり来ない場合は、ラベルなしで作成するかユーザーに確認する。新しいラベルを勝手に作らない。

### 3. タイトル

日本語で、issueの内容を簡潔に表すタイトルにする（PRのような`type:`プレフィックスは付けない）。`gh issue list`の実例:

```
指示で移動できるパターンを洗い出す
マップ生成ページでダウンロードするファイルの中身がコードにそのまま記載されていて可読性が悪い
道案内指示のルールベース解釈強化（手前/まで/右左折/直進）
```

### 4. 本文

内容の複雑さに応じて書き分ける。すべての項目を毎回埋める必要はない — その issue に意味のあるセクションだけを使う。

- **単純な内容**（一言で言い切れるバグ・タスク）: ヘッダーなしの1〜2行で十分。実例:
  ```
  生成するコードの内容は別ファイルで分かりやすく管理できる様にする
  ```
- **複雑な内容**（設計判断が必要な機能追加、再現手順や背景説明が要るバグなど）: 必要なセクションだけを使った構造化フォーマット。実例:
  ```markdown
  ## 背景
  （なぜこれが必要か）

  ## 現状の課題
  - 課題を箇条書きで

  ## 対応方針
  - 対応方針を箇条書きで

  ## 完了条件
  - 完了とみなせる状態を箇条書きで
  ```

### 5. 作成

```bash
gh issue create --title "タイトル" --label "ラベル名" --body "$(cat <<'EOF'
本文
EOF
)"
```

ラベルなしで作る場合は `--label` を省略する。

### 6. 結果報告

作成されたissueのURLをユーザーに伝えて完了とする。
